A node built with the Cosmos SDK exposes several interfaces. They are not alternatives to each other in the way the shared word "API" suggests: they sit at different layers and answer different questions.

## Interaction surfaces

| Surface | Default address | Enabled by default | What it serves |
| --- | --- | --- | --- |
| gRPC | `localhost:9090` | Yes | Application state queries, defined by each module as a `Query` service |
| REST | `tcp://localhost:1317` | No | HTTP bindings of those same query methods, generated by the gRPC gateway |
| CometBFT RPC | `tcp://127.0.0.1:26657` | Yes | Blocks, validators, the mempool, transaction broadcast, and websocket subscriptions |
| CLI | not a network service | n/a | `simd query` and `simd tx`, which call the same methods over gRPC |

The gRPC and REST surfaces are generated from the same protobuf definitions, so a method reachable at `cosmos.bank.v1beta1.Query/AllBalances` on port 9090 is reachable at `GET /cosmos/bank/v1beta1/balances/{address}` on port 1317 whenever the method carries an HTTP binding. They are two doors into one set of handlers, not two APIs.

CometBFT RPC is genuinely separate. It belongs to the consensus engine underneath the SDK, it predates the SDK's gRPC support, and it knows nothing about your application's modules. See the [CometBFT RPC reference](/cometbft/latest/api-reference/rpc/index) for its methods.

Chains that run [Cosmos EVM](/evm/latest/api-reference/ethereum-json-rpc/index) add an Ethereum JSON-RPC surface on top of these.

## Transaction messages are not a fourth surface

Every module also defines a `Msg` service. Its methods are not endpoints you call. They describe the state changes the module permits, and each one is encoded into a transaction, signed, and broadcast through one of the surfaces above:

```text
cosmos.tx.v1beta1.Service/BroadcastTx     gRPC
POST /cosmos/tx/v1beta1/txs               REST
/broadcast_tx_sync                        CometBFT RPC
```

The reference lists transaction messages separately from queries for this reason. A `Msg` handler name is useful for building a transaction and for generated clients. It is not an address you can call.

## What this reference covers

These pages document the services, transaction messages, and REST routes of the standard modules shipped with the Cosmos SDK at the version shown on each page.

The SDK is a framework, so a running chain will differ. It serves only the modules its application registers, it may add modules of its own, and it may disable routes or run a patched version. For one specific node, reflection is the authoritative answer:

```bash
grpcurl -plaintext localhost:9090 list
```

See [gRPC services](/sdk/next/api-reference/grpc/index) for more reflection recipes.

## Enabling the interfaces

gRPC is on by default. The REST API is not, so it has to be turned on in `app.toml` before port 1317 answers:

```toml
[api]
enable = true
address = "tcp://localhost:1317"

# Serves the generated OpenAPI document at /swagger.
swagger = true

[grpc]
enable = true
address = "localhost:9090"
```

CometBFT RPC is configured separately, in `config.toml`:

```toml
[rpc]
laddr = "tcp://127.0.0.1:26657"
```

Both default to localhost. Exposing either publicly needs a deliberate address change and, for browsers, CORS configuration.

## Trying a request

The REST pages include a request playground. Its default server is a community-run public endpoint serving Cosmos Hub, which is not operated by the Cosmos SDK team and runs Cosmos SDK v0.53.4 against pages documenting v0.55.

A 501 from that endpoint has two quite different causes, and the response body distinguishes them. `not implemented` means the chain does not include that module, which is the case for `epochs` on the Hub. A message naming a hosting provider, such as `Method /cosmos/auth/v1beta1/accounts is not allowed`, means the provider blocks that route because it is expensive; the chain supports it and your own node will serve it. The same providers sometimes answer `503` with a plain message like `Please use your own full node`, which means the same thing.

To use your own node instead, select `http://localhost:1317` from the server list. Note that a page served over HTTPS cannot call a plain HTTP address from the browser, so local requests are better made with the generated `curl` command than with the playground.
