title: "gRPC Services"
description: "How Cosmos SDK gRPC services are named, and how to list and call them against a running node."
---

Each module defines its API in protobuf. A `service` block groups related methods, and each `rpc` inside it declares one method with exactly one request message and one response message.

```proto
package cosmos.bank.v1beta1;

service Query {
  rpc AllBalances(QueryAllBalancesRequest) returns (QueryAllBalancesResponse) {
    option (google.api.http).get = "/cosmos/bank/v1beta1/balances/{address}";
  }
}
```

Three parts combine into the name a node answers to:

```text
cosmos.bank.v1beta1  .  Query  /  AllBalances
      package           service      method
```

The `google.api.http` option on the method is what produces the REST route on port 1317. Methods without that option are reachable over gRPC only.

## Two kinds of service

Modules define `Query` services and `Msg` services, and the SDK routes them differently.

`Query` services are registered into the gRPC query router and served on port 9090.

`Msg` services are registered into the message service router, which is consulted only while a transaction is being delivered. Their methods are not reachable on port 9090. The module pages list them under Transaction messages, with the type URL you place in a transaction rather than a `grpcurl` command.

A handful of services are named neither `Query` nor `Msg`, such as `cosmos.tx.v1beta1.Service` and the reflection services. Those are ordinary callable services and appear alongside queries.

## Scalar encodings

Field tables note an encoding on some fields, as `Encoded as cosmos.Dec`. These are not protobuf types, they are conventions the SDK layers on top of `string` and `bytes`, and getting them wrong produces wrong answers rather than errors.

| Annotation | Meaning |
| --- | --- |
| `cosmos.Int` | Arbitrary-precision integer sent as a base-10 string. `"8821829649"` is 8,821,829,649. |
| `cosmos.Dec` | A fixed-point decimal, in one of three forms. The field table says which. |
| `cosmos.AddressString` | Bech32 account address carrying the chain's prefix, `cosmos1...` on the Hub. |
| `cosmos.ValidatorAddressString` | Bech32 validator operator address, `cosmosvaloper1...` on the Hub. |
| `cosmos.ConsensusAddressString` | Bech32 validator consensus address, `cosmosvalcons1...` on the Hub. Derived from the validator's consensus key, so it is a different address from its operator address, not a reformatting of it. |

Account and validator addresses are separate address spaces. Passing an account address where a validator operator address is expected fails with `hrp does not match bech32 prefix`. The prefix is chain-specific: query `cosmos.auth.v1beta1.Query/Bech32Prefix` to find it.

### cosmos.Dec depends on which codec reads it

A `cosmos.Dec` is a fixed-point decimal, and the string that carries it means different things on different surfaces. The same value, 0.05, is written and read four ways:

| Where | Form | Example |
| --- | --- | --- |
| Writing, transaction JSON: the CLI, and `POST /cosmos/tx/v1beta1/encode` | a decimal string | `"0.05"` |
| Writing, protobuf JSON: `grpcurl`, generated clients, `Service/TxEncode` | an integer string scaled by 10^18 | `"50000000000000000"` |
| Reading over gRPC | scaled, or base64 of the scaled digits for a `bytes` field | `"50000000000000000"`, `"MTAwMDAwMDAwMDAwMDAwMDAw"` |
| Reading over REST | a decimal string | `"0.050000000000000000"` |

The field tables name the read form for each field, because that is the one that varies by field. The write form varies by codec rather than by field: transaction JSON takes the decimal, protobuf JSON takes the scaled integer.

Getting this wrong does not always error. Passing `"50000000000000000"` where a decimal is expected is read as fifty quadrillion, so a commission rate is rejected as over 100%, and a vote weight comes back as `1000000000000000000.000000000000000000`. Passing `"0.05"` where the scaled form is expected fails to parse.

Read as a plain integer, a scaled value is out by 10^18 with no error at all. `staking` `Params.min_commission_rate` returning `"50000000000000000"` is 5%, and `Delegation` returning `shares` of `"8821829649000000000000000000"` beside a `balance` of `"8821829649"` is the same number in both conventions.

Fields typed `bytes` are base64 in JSON. Passing hex will not error: it decodes as base64 and yields a valid-looking, wrong value.

A `pagination.next_key` in a response is already base64. Over gRPC, paste it back verbatim. In a REST query string, percent-encode it first: standard base64 emits `+`, which a query string reads as a space, and the key is then rejected as malformed.

A `bytes` value that appears in a REST path segment rather than a query parameter needs base64url, with `-` and `_` in place of `+` and `/`. A `/` in standard base64 breaks the path even when percent-encoded.

Amounts are always in the chain's base denomination, never the display one. On the Hub the base denom is `uatom` and 1 ATOM is `1000000uatom`. Find a chain's denominations with `cosmos.staking.v1beta1.Query/Params` for `bond_denom`, or by paging `cosmos.bank.v1beta1.Query/DenomsMetadata`.

A field typed `Any` carries an `@type` discriminator naming the concrete message, with that message's fields inline beside it. `cosmos.auth.v1beta1.Query/Account` returns one, and what comes back depends on the account: `BaseAccount`, `ModuleAccount`, or a vesting account type.

Protocol buffers version 3 omits fields holding their default value, so a successful query that matched nothing returns `{}` rather than an empty list. An empty result and a mistaken query look identical.

## Listing what a node actually serves

These pages document the standard modules at one SDK version. A specific chain registers its own set. gRPC reflection asks the node directly, and is the authoritative answer for that node:

```bash
# Every service the node serves
grpcurl -plaintext localhost:9090 list

# Every method on one service
grpcurl -plaintext localhost:9090 list cosmos.bank.v1beta1.Query

# The full request and response schema for one method
grpcurl -plaintext localhost:9090 describe cosmos.bank.v1beta1.Query.AllBalances

# The fields of a request message
grpcurl -plaintext localhost:9090 describe cosmos.bank.v1beta1.QueryAllBalancesRequest
```

## Calling a method

Pass the request as JSON with `-d`. Field names accept either the protobuf name or its JSON form, so `resolve_denom` and `resolveDenom` both work:

```bash
grpcurl -plaintext -d '{"address": "cosmos1..."}' \
  localhost:9090 cosmos.bank.v1beta1.Query/AllBalances
```

Against a TLS endpoint, drop `-plaintext` and use port 443:

```bash
grpcurl -d '{"address": "cosmos1..."}' \
  cosmos-grpc.example.com:443 cosmos.bank.v1beta1.Query/AllBalances
```

If reflection is disabled on the node, `grpcurl` needs the protos locally and the `-import-path` and `-proto` flags instead.

## Pagination

Queries returning a list take a `pagination` field and return one alongside their results. Request either an offset or a key, never both:

```bash
grpcurl -plaintext \
  -d '{"address": "cosmos1...", "pagination": {"limit": 10, "count_total": true}}' \
  localhost:9090 cosmos.bank.v1beta1.Query/AllBalances
```

The response carries `pagination.next_key`. Pass it back as `pagination.key` for the following page. Key-based paging is cheaper than offset paging and is the right choice for walking a large result set.
