<HubVerified date="2026-10-15" log="https://github.com/cosmos/docs" />

You need a machine that meets the [system requirements](/hub/latest/getting-started/system-requirements) and a verified `gaiad` from [Install gaiad](/hub/latest/getting-started/installation). At the end you have a full node on `cosmoshub-4` that is catching up or caught up, with configuration you set through `gaiad config` rather than by editing TOML by hand. A validator starts as exactly this node; the validator pages add the keys and the transaction on top.

Commands below use the default home `~/.gaia`. Add `--home <path>` to every command if you keep the node elsewhere, and set `GAIAD_HOME` in the service environment so the unit on [Run gaiad as a service](/hub/latest/node/service) agrees.

<Steps>
  <Step title="Initialize the home directory">
    ```bash
    gaiad init my-hub-node --chain-id cosmoshub-4
    ```

    This creates `~/.gaia/config` with `config.toml`, `app.toml`, `client.toml`, a placeholder `genesis.json`, `node_key.json`, and `priv_validator_key.json`, plus `~/.gaia/data/priv_validator_state.json`. The moniker is a display name for peers and explorers; use ASCII only, since a Unicode moniker makes the node unreachable. The command prints the node id and the new genesis as JSON; the printed genesis is a throwaway that the next step replaces.

    The init also generates the two key files a validator will care about later. `node_key.json` is the peer to peer identity and can be regenerated at any time. `priv_validator_key.json` is the consensus key; on a full node it signs nothing, on a validator it signs blocks and cannot be rotated on the Hub today, so if this machine will become a validator, back that file up now and never copy it to a second running node. [Security](/hub/latest/validators/security) covers key handling.

    Check:

    ```bash
    ls ~/.gaia/config
    gaiad comet show-node-id
    ```
  </Step>

  <Step title="Install the genesis file">
    ```bash
    cd "$(mktemp -d)"
    curl -LO https://raw.githubusercontent.com/cosmos/mainnet/master/genesis/genesis.cosmoshub-4.json.gz
    sha256sum genesis.cosmoshub-4.json.gz
    gzip -d genesis.cosmoshub-4.json.gz
    mv genesis.cosmoshub-4.json ~/.gaia/config/genesis.json
    ```

    The checksum of the gzipped file is `7fe946e6bb3c378da546767f4d078585c38f256c8ec17888d71aeee3b7edd5c7`, as published in the [cosmos/mainnet genesis checksum file](https://github.com/cosmos/mainnet/blob/master/genesis/genesis_checksum.md). The file is about 21 MB compressed. `cosmoshub-4` launched on 2021-02-18 at height 5200791 from the exported state of `cosmoshub-3`, so this genesis is not an empty chain. The `genesis_time` field still carries the `cosmoshub-3` date (2019-12-11), and block 5200791 repeats it; the first real block, 5200792, is timestamped 2021-02-18.

    Check:

    ```bash
    jq -r '.chain_id, .initial_height, .genesis_time' ~/.gaia/config/genesis.json
    ```

    This prints `cosmoshub-4`, `5200791`, and `2019-12-11T16:11:34Z`. Do not use `gaiad genesis validate` on this file: the 2019 genesis predates several module formats and v28.3.1 reports `section is missing in the app_state`, even though the node bootstraps from it without trouble. The checksum is the real check.
  </Step>

  <Step title="Set the client defaults">
    ```bash
    gaiad config set client chain-id cosmoshub-4
    gaiad config get client chain-id
    ```

    This writes `chain-id = "cosmoshub-4"` to `client.toml`, so every later `gaiad query` and `gaiad tx` on this machine targets the right chain without a `--chain-id` flag. `gaiad config` is the confix tool; `get` reads a key back, `view client` prints the whole file.
  </Step>

  <Step title="Set the minimum gas price">
    ```bash
    gaiad config set app minimum-gas-prices 0.005uatom
    gaiad config get app minimum-gas-prices
    ```

    This sets `minimum-gas-prices` in `app.toml`. The Hub prices transactions with the feemarket module, whose floor is 0.005uatom; a node that accepts cheaper transactions into its mempool just carries spam that no block will include. Fees work out as `fees = ceil(gas * gasPrices)`, and the live price is one query away:

    ```bash
    curl -s https://cosmos-rest.publicnode.com/feemarket/v1/gas_price/uatom | jq -r '.price.amount'
    ```

    On 2026-10-15 this returned `0.005000000000000000`. The TOML key is `minimum-gas-prices` at the top of `app.toml`.
  </Step>

  <Step title="Add seeds">
    ```bash
    SEEDS=$(curl -s https://raw.githubusercontent.com/cosmos/chain-registry/master/cosmoshub/chain.json | jq -r '[.peers.seeds[] | "\(.id)@\(.address)"] | join(",")')
    echo "$SEEDS"
    gaiad config set config p2p.seeds "$SEEDS" -s
    gaiad config get config p2p.seeds
    ```

    This writes `seeds` in the `[p2p]` section of `config.toml` from the chain registry's seed list, which had ten entries on 2026-10-15, for example `ade4d8bc8cbe014af6ebdf3cb7b1e9ad36f412c0@seeds.polkachu.com:14956`. Seeds hand your node a list of peers and disconnect; the node then fills its 40 inbound and 10 outbound slots on its own. Persistent peers (`p2p.persistent_peers`, from `.peers.persistent_peers` in the same file) are for nodes you want to stay connected to, such as your own sentries.

    `-s` (`--skip-validate`) is required for every `config.toml` key: without it `gaiad config set config` on v28.3.1 fails with `cometbft config is not supported`. The write is still a plain TOML edit, and `gaiad config get config <key>` reads the result back without the flag.
  </Step>

  <Step title="Choose pruning and the database backend">
    Decide both before the first sync; neither changes in place later.

    ```bash
    gaiad config set app pruning default
    gaiad config get config db_backend
    ```

    `pruning = "default"` keeps the last 362880 application states (about three weeks) and prunes every 10 blocks, which fits a validator or a general RPC node. `nothing` makes an archive node, `everything` keeps only the two latest states, and `custom` takes `pruning-keep-recent` and `pruning-interval`. `pruning-keep-every` no longer exists. A pruned node cannot answer queries for heights it has pruned.

    `db_backend` defaults to `goleveldb`. To run on PebbleDB, set `gaiad config set config db_backend pebbledb -s` and `gaiad config set app app-db-backend pebbledb` now, and restore a PebbleDB snapshot in the next step. [Database backends](/hub/latest/node/database) explains the choice.
  </Step>

  <Step title="Sync the node">
    A new node has three ways to reach the chain tip: a snapshot from a provider, state sync from public RPCs, or block sync from genesis. Block sync from genesis is not practical on the Hub because every historical upgrade must be replayed with its own binary, so use one of the first two. [Sync a node](/hub/latest/node/sync) has the provider table, the state sync configuration, and the troubleshooting for both. Come back here when the data directory is in place or state sync is configured.
  </Step>

  <Step title="Start the node">
    Run it in the foreground once to watch the first minutes of logs:

    ```bash
    gaiad start
    ```

    The node starts CometBFT, connects to peers, and either restores the state sync snapshot or begins applying blocks on top of the restored data. The log lines to look for are `Discovered new snapshot` and `Applied snapshot chunk` during state sync, then `executed block height=... module=state` and `committed state` as it catches up. Stop it with Ctrl-C once it is applying blocks and move it under systemd on [Run gaiad as a service](/hub/latest/node/service).

    Old guides add `--x-crisis-skip-assert-invariants`; the crisis module is gone and v28.3.1 refuses to start with that flag.
  </Step>
</Steps>

## Optional servers

The REST API is off by default; gRPC is on and bound to `localhost:9090`. Turn either on only on a machine that is meant to serve queries, never on a validator.

```bash
gaiad config set app api.enable true
gaiad config set app api.address tcp://0.0.0.0:1317
gaiad config set app grpc.address 0.0.0.0:9090
```

The TOML sections are `[api]` and `[grpc]` in `app.toml`. For Prometheus metrics, set `gaiad config set config instrumentation.prometheus true -s`, which opens `:26660`. [Endpoints](/hub/latest/infrastructure/endpoints) covers running these publicly.

## Export state

`gaiad export` writes the full application state as JSON, which is how a new network or a migration test starts from Hub state. The node must be stopped first or the command fails with `resource temporarily unavailable`.

```bash
gaiad export > export.json
gaiad export --height <height> --for-zero-height > new_genesis.json
```

`--height` exports the state after that block; `--for-zero-height` rewrites it so the file can start a new chain at height 0. `--modules-to-export` limits the output to a comma separated module list.

## Verify

With the node running, from the same machine:

```bash
gaiad status | jq '{id: .node_info.id, network: .node_info.network, height: .sync_info.latest_block_height, catching_up: .sync_info.catching_up}'
```

`network` must be `cosmoshub-4`. `catching_up` turns `false` once the node reaches the tip; compare `height` with the height on [Mintscan](https://www.mintscan.io/cosmos) or with `curl -s https://cosmos-rpc.polkachu.com/status | jq -r .result.sync_info.latest_block_height`. Peer count comes from `curl -s localhost:26657/net_info | jq .result.n_peers`; a healthy node shows ten or more.
