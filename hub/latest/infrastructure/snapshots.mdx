This page is for operators who want a Cosmos Hub node synced in hours rather than days, and for operators who publish snapshots. It assumes gaia is installed and the home directory is initialized (see [Join mainnet](/hub/latest/hub-tutorials/join-mainnet)). At the end the node starts from a recent height and catches up from peers.

Two things are both called snapshots on the Hub. A data snapshot is a tar archive of the `data` directory that you download and extract. A state sync snapshot is produced inside the node (`[state-sync]` in `app.toml`) and fetched over P2P by [state sync](/hub/latest/node/sync). This page covers data snapshots, and the last section covers producing state sync snapshots for others.

## Pick a snapshot that matches your backend

The snapshot's database format must match the `app-db-backend` in `app.toml` and the `db_backend` in `config.toml` of the node that restores it. A PebbleDB node cannot open goleveldb files and the other way round. Provider pages do not always state the backend; when they do not, assume goleveldb or ask. Backend choice and migration are explained on [Database and pruning](/hub/latest/node/database).

Snapshot archives are made from pruned nodes. A pruned snapshot cannot be turned into an archive node; for that see [Archive nodes](/hub/latest/resources/archives).

## Restore a data snapshot

A restore is a stop, a reset that keeps the validator state file, an extract into `data/`, and a start; the validator state file is the step that matters.

1. Stop the node and back up the validator state file. On a validator this file is what stops the node from double signing after a restore.

```bash
sudo systemctl stop gaiad
cp ~/.gaia/data/priv_validator_state.json ~/priv_validator_state.json.bak
```

2. Reset the data directory, keeping the address book so the node reconnects quickly:

```bash
gaiad comet unsafe-reset-all --home ~/.gaia --keep-addr-book
```

3. Download the archive and its checksum, and compare them before extracting. The file names and checksum formats are on the provider's page.

```bash
sha256sum -c cosmoshub-4-snapshot.tar.lz4.sha256
```

4. Extract into the home directory. Most archives contain `data/` and some also contain `wasm/`; a PebbleDB provider that ships `wasm` as a separate archive needs both extracted.

```bash
lz4 -dc cosmoshub-4-snapshot.tar.lz4 | tar -xf - -C ~/.gaia
```

5. Put the validator state back and start:

```bash
cp ~/priv_validator_state.json.bak ~/.gaia/data/priv_validator_state.json
sudo systemctl start gaiad
```

<Warning>
On a validator, restoring a snapshot that carries someone else's `priv_validator_state.json`, or starting with a fresh one, can make the node sign a height it already signed. That is a double sign and the slash is 5 percent of stake plus permanent tombstoning. Always restore your own copy of the file.
</Warning>

## Make snapshots for others

A snapshot node is a pruned full node (`pruning = "custom"`, `pruning-keep-recent = "100"`, `pruning-interval = "10"` is common) that is stopped on a schedule, tarred, and started again. Stop the node first; archiving a live database produces a corrupt snapshot.

```bash
sudo systemctl stop gaiad
tar -cf - -C ~/.gaia data wasm | lz4 -c > cosmoshub-4_$(date -u +%Y%m%d)_$(gaiad status 2>/dev/null | jq -r .sync_info.latest_block_height).tar.lz4
sudo systemctl start gaiad
```

Publish next to each archive: the height, the gaia version, the database backend (`pebbledb` or `goleveldb`), the pruning settings, whether `wasm` is included, and a SHA-256 checksum. Strip `data/priv_validator_state.json` from the archive or document that it is in there.

## Serve state sync snapshots

State sync snapshots are made by the running node and need no stop. Enable them in `app.toml`:

```bash
gaiad config set app state-sync.snapshot-interval 1000
gaiad config set app state-sync.snapshot-keep-recent 2
```

```toml
[state-sync]
snapshot-interval = 1000
snapshot-keep-recent = 2
```

`snapshot-interval` is in heights; the default `gaiad init` writes is 1000 with 10 kept. Snapshots are only taken at heights that are a multiple of the interval, and the node must have the state at that height, so a node that prunes more aggressively than the interval cannot produce them. List what the node holds:

```bash
gaiad snapshots list
```

The output is empty on a fresh node and lists `height`, `format` and `chunks` once snapshots exist. `gaiad snapshots export --height <h>` takes one on demand, `gaiad snapshots dump <height> <format>` writes it to an archive file, and `gaiad snapshots load <archive-file>` plus `gaiad snapshots restore <height> <format>` bring one into another node without P2P. Consumers also need two RPC endpoints with these snapshots to configure `[statesync]`; see [Sync options](/hub/latest/node/sync).

## Verify

After a restore, the node should report the snapshot height and then advance:

```bash
gaiad status | jq '.sync_info | {latest_block_height, catching_up}'
```

`latest_block_height` starts at the snapshot height and `catching_up` turns `false` once the node is within a few blocks of the network. If the node logs `panic: ... pebble` or `leveldb` read errors at start, the archive did not match the configured backend.
