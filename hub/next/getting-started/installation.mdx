You need a machine that meets the [system requirements](/hub/next/getting-started/system-requirements) and the version you are installing from the [Versions](/hub/next/start/versions) page. At the end you have a `gaiad` binary (or image) that reports `v28.3.1` and that you have verified against the release signature or built yourself. All three options are equal. Pick the one that fits how you run servers.

## Pick the version first

Install the current mainnet release tag, not the newest tag. Release candidates (`-rc`) are for the testnet.

```bash
curl -s https://cosmos-rpc.polkachu.com/abci_info | jq -r '.result.response.version'
```

On 2026-10-15 this printed `v28.3.1`. The examples below use that tag. Replace it if the chain has moved on.

## Install

<Tabs>
  <Tab title="Signed release binary">
    Each gaia release ships `gaiad-linux-amd64.tar.gz` and `gaiad-darwin-amd64.tar.gz`, a detached GNU Privacy Guard (GPG) signature (`.asc`) for each, and `SHA256SUMS-<tag>.txt`. The release is signed with the Cosmos release key, fingerprint `E625 9F16 9C7B 913D BB75 DE02 5395 305D 29B8 8B32`, published in the [cosmos/security](https://github.com/cosmos/security/tree/main/release/gaia/signing) repository. There is no arm64 Linux binary. Use the source build on arm64.

    Import the release key once:

    ```bash
    curl -sL https://raw.githubusercontent.com/cosmos/security/main/release/gaia/signing/keys/cosmos-release.asc | gpg --import
    gpg --fingerprint nodes@cosmoslabs.io
    ```

    The fingerprint printed must match the one above. If it does not, stop. Do not install.

    Download the tarball, its signature, and the checksum file:

    ```bash
    export GAIA_TAG=v28.3.1
    cd "$(mktemp -d)"
    curl -LO "https://github.com/cosmos/gaia/releases/download/${GAIA_TAG}/gaiad-linux-amd64.tar.gz"
    curl -LO "https://github.com/cosmos/gaia/releases/download/${GAIA_TAG}/gaiad-linux-amd64.tar.gz.asc"
    curl -LO "https://github.com/cosmos/gaia/releases/download/${GAIA_TAG}/SHA256SUMS-${GAIA_TAG}.txt"
    ```

    Verify the signature, then the checksum:

    ```bash
    gpg --verify gaiad-linux-amd64.tar.gz.asc gaiad-linux-amd64.tar.gz
    tar -xzf gaiad-linux-amd64.tar.gz
    sha256sum --check --ignore-missing "SHA256SUMS-${GAIA_TAG}.txt"
    ```

    Expect `Good signature from "Cosmos-Release <nodes@cosmoslabs.io>"` from `gpg --verify` and `./gaiad-linux-amd64/gaiad: OK` from `sha256sum --check`. A warning that the key is not certified is normal for a key you imported directly. A `BAD signature` line is not, and `Can't check signature: No public key` means the import did not reach the keyring gpg uses. On macOS use `shasum -a 256 --check --ignore-missing`.

    Install the binary where your service user can run it:

    ```bash
    sudo install -m 0755 gaiad-linux-amd64/gaiad /usr/local/bin/gaiad
    ```

    The `install` command copies the file and sets the mode in one step, and `/usr/local/bin` is on `PATH` for every user, including the service user on [Run gaiad as a service](/hub/next/node/service).
  </Tab>
  <Tab title="Container image">
    The release workflow publishes `ghcr.io/cosmos/gaia:<tag>` for every release tag (for example `ghcr.io/cosmos/gaia:v28.3.1`), plus a `nightly` tag from main. There is no `latest` tag, which is deliberate. Pin the current mainnet release tag. The image is a static linux/amd64 build with `gaiad start` as its entrypoint. It runs as user `nonroot` (uid 1025) and exposes ports 26656, 26657, 1317, and 9090.

    Pull the image and check the version:

    ```bash
    docker pull ghcr.io/cosmos/gaia:v28.3.1
    docker run --rm --entrypoint gaiad ghcr.io/cosmos/gaia:v28.3.1 version --long | grep -E '^(version|commit):'
    ```

    The image stamps the version as `HEAD-<commit>`, so this prints `version: HEAD-b7f8b81bd4bd3df697d484cbb5577c1382435243`. Match the commit against the [v28.3.1 release page](https://github.com/cosmos/gaia/releases/tag/v28.3.1). The commit is the proof, not the version string.

    Mount a host directory as the node home so the data survives the container. The gaia repository's convention is `/opt/gaia`:

    ```bash
    sudo mkdir -p /opt/gaia && sudo chown 1025:1025 /opt/gaia
    docker run --rm -it -v /opt/gaia:/opt/gaia --entrypoint gaiad ghcr.io/cosmos/gaia:v28.3.1 init my-hub-node --chain-id cosmoshub-4 --home /opt/gaia
    ```

    This writes `config/` and `data/` under `/opt/gaia` on the host, owned by uid 1025. Every `gaiad` command on the [Join mainnet](/hub/next/hub-tutorials/join-mainnet) page then takes the form `docker run --rm -v /opt/gaia:/opt/gaia --entrypoint gaiad ghcr.io/cosmos/gaia:v28.3.1 <command> --home /opt/gaia`. The node itself runs with the default entrypoint:

    ```bash
    docker run -d --name gaiad --restart unless-stopped -p 26656:26656 -v /opt/gaia:/opt/gaia ghcr.io/cosmos/gaia:v28.3.1 --home /opt/gaia
    ```

    To upgrade, change the tag at the upgrade height. Cosmovisor does not run inside this image, so follow the manual sequence on [Upgrade a node](/hub/next/hub-tutorials/upgrade-node).
  </Tab>
  <Tab title="Source build">
    Build from the release tag with the Go version pinned in that tag's `go.mod`. For v28.3.1 that is Go 1.25.7 or any later 1.25 patch (1.25.14 was current on 2026-10-15). The Makefile refuses older Go, and Go 1.27 fails to compile a dependency.

    Install the build tools and Go:

    ```bash
    sudo apt update && sudo apt install -y make gcc git curl
    curl -LO https://go.dev/dl/go1.25.14.linux-amd64.tar.gz
    sudo rm -rf /usr/local/go && sudo tar -C /usr/local -xzf go1.25.14.linux-amd64.tar.gz
    export PATH=$PATH:/usr/local/go/bin:$(go env GOPATH 2>/dev/null || echo "$HOME/go")/bin
    go version
    ```

    Running `go version` prints `go1.25.14`. Add the `PATH` line to your shell profile so it survives a new login. On arm64 download `go1.25.14.linux-arm64.tar.gz` instead.

    Clone the repository at the tag and build:

    ```bash
    git clone https://github.com/cosmos/gaia.git && cd gaia
    git checkout v28.3.1
    CGO_ENABLED=1 make install
    ```

    The `make install` target compiles with the `netgo,ledger` build tags and places `gaiad` in `$(go env GOPATH)/bin`. Wasmvm is a C library, so a build without `CGO_ENABLED=1` fails at link time. The `make build` target writes to `./build/gaiad` instead.

    If the build fails with `flag provided but not defined: -L`, an `LDFLAGS` variable from your environment is leaking into the Go linker. Run `LDFLAGS="" make install`.

    A source build is the only option with the `ledger` build tag, which `gaiad keys add --ledger` needs. It is not bit for bit identical to the release binary. For one you can compare to the published checksums, follow [Reproducible builds](/hub/next/resources/reproducible-builds).
  </Tab>
</Tabs>

## Verify

```bash
gaiad version --long | grep -E '^(name|version|commit|cosmos_sdk_version|go|build_tags):'
```

Expected for the current release:

```text
build_tags: netgo,muslc
commit: b7f8b81bd4bd3df697d484cbb5577c1382435243
cosmos_sdk_version: v0.53.4
go: go version go1.25.7 linux/amd64
name: gaia
version: v28.3.1
```

The `commit` is the git commit of the tag and is the same for every install method. It is the line to compare. The `version` line reads `v28.3.1` for the release tarball and a source build at the tag. It reads `HEAD-b7f8b81bd4bd3df697d484cbb5577c1382435243` for the container image. The `build_tags` line reads `netgo,ledger` for a source build. It reads `netgo,muslc` for the release tarball and the container image, which are static musl builds without Ledger support. The `go` line shows the toolchain the binary was built with. A source build with a later 1.25 patch shows that patch instead of 1.25.7. For the container image, run the same command with `docker run --rm --entrypoint gaiad ghcr.io/cosmos/gaia:v28.3.1 version --long`.

## Build tags

| Build tag | Meaning |
| --- | --- |
| netgo | Name resolution uses pure Go code |
| ledger | Ledger hardware wallets are supported by `gaiad keys`; present on a source build only |
| muslc | wasmvm is statically linked against musl; present on the release tarball and container builds, which do not carry `ledger` |
