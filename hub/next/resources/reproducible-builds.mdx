This page is for operators who want proof that the `gaiad` they run is the one the gaia maintainers published, or who build it themselves. [Installation](/hub/next/getting-started/installation) covers the quick path; this page covers what sits behind each option.

## Release artifacts

Each gaia release on GitHub (`https://github.com/cosmos/gaia/releases/tag/v28.3.1`, published 2026-10-01) ships:

- `gaiad-v28.3.1-linux-amd64` and `gaiad-v28.3.1-darwin-amd64`: bare binaries, each with a detached signature `.asc`.
- `gaiad-linux-amd64.tar.gz` and `gaiad-darwin-amd64.tar.gz`: the same binaries in a directory with a `sha256sum.txt`, each with a detached signature `.asc`.
- `SHA256SUMS-v28.3.1.txt`: SHA-256 of the binaries as extracted from the archives (`./gaiad-linux-amd64/gaiad`, `./gaiad-darwin-amd64/gaiad`).

There is no arm64 build. The release configuration (`.goreleaser.yml` in the gaia repository) disables it because the static wasmvm library the Hub's CosmWasm module links against is built for amd64 only. Operators on arm64 hosts build from source or run the amd64 image under emulation.

## Check a download

Releases are signed with the Cosmos release key, published with instructions in the `cosmos/security` repository (`https://github.com/cosmos/security/tree/main/release/gaia/signing`). Fingerprint: `E625 9F16 9C7B 913D BB75 DE02 5395 305D 29B8 8B32`, identity `Cosmos-Release <nodes@cosmoslabs.io>`.

```bash
curl -sLO https://github.com/cosmos/gaia/releases/download/v28.3.1/gaiad-linux-amd64.tar.gz
curl -sLO https://github.com/cosmos/gaia/releases/download/v28.3.1/gaiad-linux-amd64.tar.gz.asc
curl -sLO https://github.com/cosmos/gaia/releases/download/v28.3.1/SHA256SUMS-v28.3.1.txt
curl -sLO https://raw.githubusercontent.com/cosmos/security/main/release/gaia/signing/keys/cosmos-release.asc
gpg --show-keys --with-fingerprint cosmos-release.asc
gpg --import cosmos-release.asc
gpg --verify gaiad-linux-amd64.tar.gz.asc gaiad-linux-amd64.tar.gz
tar -xzf gaiad-linux-amd64.tar.gz
sha256sum -c --ignore-missing SHA256SUMS-v28.3.1.txt
```

`--show-keys` prints the fingerprint of the downloaded key; compare it against the one above before importing. `gpg --verify` must print `Good signature from "Cosmos-Release <nodes@cosmoslabs.io>"` with that fingerprint; the `WARNING: This key is not certified with a trusted signature` line that follows only means your local GPG has not been told to trust the key, and is not a failure. `sha256sum -c` prints `./gaiad-linux-amd64/gaiad: OK`. Do not run a binary whose signature fails, is from another key, or whose checksum does not match. The bare binaries verify the same way with their own `.asc`.

The extracted binary is a static PIE executable (`file gaiad` reports `static-pie linked`), so it runs on any x86-64 Linux without extra libraries.

## Docker image

The release workflow also publishes `ghcr.io/cosmos/gaia` with the version as the tag:

```bash
docker pull ghcr.io/cosmos/gaia:v28.3.1
docker run --rm ghcr.io/cosmos/gaia:v28.3.1 version --long
```

The image (`Dockerfile` in the repository) builds `gaiad` on `golang:1.25.7-alpine` with a statically linked musl wasmvm, copies only the binary into an Alpine base, runs as user `nonroot` (uid 1025), exposes 26656, 26657, 1317 and 9090, and has `gaiad start` as its entrypoint, so arguments to `docker run` are `gaiad` subcommands. Mount the home directory at a path the `nonroot` user can write and pass `--home`; the [service page](/hub/next/node/service) covers running it under systemd or compose.

## Build from source

```bash
git clone https://github.com/cosmos/gaia
cd gaia && git checkout v28.3.1
make install
```

`make install` runs `go install` with the repository's build flags and places `gaiad` in `$GOPATH/bin`; `make build` puts it in `build/` instead. The Makefile refuses Go older than 1.25 (`check_version`), and v28.3.1 was released with Go 1.25.7. Default build tags are `netgo` and `ledger`; `ledger` needs `gcc`, and `LEDGER_ENABLED=false make install` drops it on hosts without a compiler. The linker flags stamp the version, commit, build tags and CometBFT version into the binary, which is what `gaiad version --long` prints, and `-trimpath` strips local paths. `GAIA_BUILD_OPTIONS=nostrip` keeps debug symbols; `LINK_STATICALLY=true` with `BUILD_TAGS=muslc` and a musl wasmvm produces the static binary the Docker image uses.

A source build on your own machine gives the same version and commit as the release but not a byte-identical file, because the release is cross compiled in a container with a static wasmvm. Treat source builds as trusted because you built them from a checked out tag, and release downloads as trusted because the signature verifies.

## How releases are built

Releases are produced by `.github/workflows/release.yml` running goreleaser inside the `goreleaser-cross` image, with the configuration in `.goreleaser.yml`: `CGO_ENABLED=1`, tags `netgo,ledger,static_wasm`, `-trimpath -mod=readonly`, a `mod_timestamp` fixed to the commit time, and the same version ldflags as the Makefile. `make goreleaser-build-local` runs that configuration on a workstation with Docker (`release --snapshot --skip=publish`) and is the way to reproduce the release build environment; expect it to run for a long time.

## Verify

```bash
gaiad version --long | head -n 8
```

Expect `version: v28.3.1`, `commit: b7f8b81b` followed by the full hash, `build_tags: netgo,ledger,static_wasm` for a release binary (`netgo,ledger` for a default source build), `go: go version go1.25.7`, and `cosmos_sdk_version: v0.53.4`. A different commit for the same version string means the binary was not built from the release tag.
